## 目的・全体像

Android / iPhone / PCへURLで配布でき、ホーム画面から起動できるPWAを追加する。既存Swift版を削除・上書きせず、PWAを今後の配布の中心にする。
画面は「ホーム / 時間割 / 記事 / メモ / その他」。掲示板はPWAのタブ、ホーム、授業詳細、検索、直接ルートに出さない。既存Swift版の保存データ・画面はそのまま残る。
記事はNotionで執筆し、アプリには公開URLと一覧用情報だけ登録。アプリ独自の本文エディタ・架空の記事の本番配信は廃止する。

利用フロー: URLを開く→任意でインストール→記事を探す→詳細でNotionを読む→ブックマーク→投稿者名からその人の記事へ。投稿時は匿名セッションを自動準備→公開URLとタイトル入力→プレビュー→登録。メールやGoogleのログイン画面は出さない。

## 仕様

### S1 PWAと既存機能

- 提案構成は web/ にTypeScriptの独立Webアプリ。manifest、192/512px・maskableアイコン、standalone、Service Worker、HTTPS配布手順、深いURLの復帰を備える。ツールの細部は実装担当が既存構成と保守性で選ぶ。
- ホーム、日/週/月時間割、個人修正、メモと画像/チェック/固定、施設・リンク、教室地図、4テーマと背景をWebへ移植。端末内データはIndexedDB。保存失敗・容量不足・復元失敗を表示し、読み込めない保存データを上書きしない。
- 既知の履修登録確認票・年間予定表PDFの解析はブラウザ内で行う。再取込差分・個人修正の保護を移植し、未知PDF/OCRは対象外。原本や個人情報を記事サーバーへ送信しない。
- アプリ本体・端末内の予定/メモ/地図は初回読込後にオフライン対応。Notion本文と記事の最新集計は通信が必要。更新通知→編集中の保存→更新の順とし、自動リロードで入力を失わない。
- iOSのEventKitはWebから使えない。本人回答によりPWAでは外部カレンダー連携を初回対象外と確定し、ローカル時間割を維持する。Swift版のOutlook読取は残る。Microsoft Graph連携は初回対象外。設定にも接続操作を出さない。
- Swiftの保存領域とブラウザは別。PWAは初回新規データで開始しPDFを再取込できる。既存メモ/画像/修正/下書きの自動移行はない。旧Swift版は未運用・データは仮のものという本人回答により、旧データ移送は初回対象外と確定。初期データに旧版の仮データを混ぜず、空の個人データから開始する。Swift版とその仮データは削除しない（Q2）。
- iOSのHEICはブラウザ差を検証し、非対応形式は理由付きで案内する。OSのプッシュ通知、App Store/Play Store配信、ネイティブ同等の全OS機能は対象外。

### S2 記事の登録

- 必須: HTTPSのNotion公開URL、タイトル（1–120字）。任意: 紹介文（280字まで）、カテゴリ、既存講義ID。投稿者はサーバーで認証された匿名ユーザーIDから設定し、表示名で同一性を判断しない。
- 初回は notion.site / notion.so と正しいサブドメインを検証対象とする。認証情報付きURL、別スキーム、偽装ホストを拒否。独自ドメイン対応は初回対象外と入力欄に表示する。
- 公開URLを保存し、公式の埋め込み機能で得るURLを用いて表示する。通常URLからの対応可否は実装の最初に実ページで検証する。必要時のみ公式「このページを埋め込む」でコピーしたコードを補助入力し、許可ホストのsrcだけを抽出してHTML自体は実行しない。任意URLへのサーバーfetchや非公式のNotion本文取得を前提にしない。
- Notionへのログイン不要で見られる公開ページを対象に、投稿前プレビューで本人が確認する。クロスオリジンのiframeのloadだけで公開・表示成功とは断定しない。
- 投稿者本人のみ登録情報の編集/削除が可能。URL正規化と二重送信防止で重複登録を抑止。失敗時は入力を保持。Notionの内容自体の編集はNotionで行う。

### S3 一覧・閲覧・投稿者

- 一覧はタイトル/紹介文検索、カテゴリ・講義の絞込、「すべて / ブックマーク」。カードに投稿者、閲覧数、ブックマーク数を表示。
- 詳細は記事情報とブックマーク操作をアプリ側に置き、その下へNotionを埋め込む。本文はNotionの表示で、アプリテーマが内部の表示を変更する保証はない。
- 元ページへのリンクを常設。読込待ち、オフライン、非公開化/削除/表示制限の場合に「再読み込み」「Notionで開く」を用意。タイムアウトは表示失敗の断定に使わない。
- 投稿者名を押すと安定したauthor_idでそのユーザーがアプリに投稿した記事を表示する。これはNotionページの作成者認証を意味しない。元の検索/講義文脈へ戻れる。
- 空一覧、検索該当なし、ブックマークなし、取得失敗、削除された記事、匿名セッションの準備失敗をそれぞれ表示する。

### S4 共通保存と集計

- 現状は共有サーバーなし。提案はCloudflare Workers Static Assets（PWA本体）＋Workers（API/匿名認証）＋D1（共有DB）。D1をブラウザへ直接公開せず、WorkerのDB bindingから操作する。契約・費用・本番公開は未実施。接続先がない段階は明示したローカル検証のみとし、端末内サンプルを共有機能の完成扱いにしない。
- データ: profiles(id,display_name)、articles(id,author_id,public_url,embed_url,title,summary,category,course_id,created_at)、bookmarks(user_id,article_id)、view_events(article_id,viewer_key,day_jst)。記事とプロフィールの公開項目だけ読取可能にする。
- ブックマークはユーザー×記事で一意。追加/解除は冪等、集計はDBで算出する。自分の保存のみ変更可。匿名ユーザーID単位の保存件数を示し（実人数とは限らない）、再試行/多重タップ/同時操作で加算が重複しない。失敗時は表示を戻して再試行を案内する。
- 閲覧数はこのアプリ内で記事詳細を開いた記録。Notion側のPV、実読了数、埋め込み成功数ではない。同一利用者・記事・日本時間の同一日につき1回を提案。匿名セッションがある場合は匿名ユーザーID、閲覧のみの場合はブラウザのランダム識別子を用いる。初回セッション作成時の同日分は同じ閲覧キーに対応付け、作成前後で二重加算しない。別端末・保存消去をまたぐ厳密な重複排除は保証しない。
- 集計への直接更新を許可せずサーバー側で一意制約・原子的更新・制限を適用。クライアントへ秘密鍵を置かない。投稿権限と他ユーザーのブックマーク変更拒否を検証する。
- 通信できない時は最後の取得値を「前回取得」と表示するか未取得を「—」にする。失敗を0件に置換しない。オフラインで投稿/ブックマークの成功を表示しない。
- 認証方式は端末ごとの匿名ユーザーで確定（Q1）。初回の投稿・保存時にサーバーで匿名セッションを発行し、このブラウザに保持する。メール・Googleログインやアカウント登録画面は設けない。セッション準備に失敗したら入力を保ち再試行できる。ユーザーが任意に指定したIDだけで投稿・編集権限を認めず、Workerで暗号学的に安全なランダムセッションを発行し、HttpOnly・Secure・SameSite Cookieに保存する。D1にはトークンのハッシュとユーザーID・有効期限を保存してリクエストを照合する。書込APIはOrigin等を検証してCSRFを防ぐ。匿名セッション発行/書込にレート制限を設ける。D1に認証機能が内蔵されている前提にはしない。
- 同じブラウザで再起動しても、セッションが保持されている限り投稿者IDとブックマークを復元する。別端末・別ブラウザは別ユーザー。ブラウザデータ削除・匿名セッション喪失後は、以前のブックマークと投稿の編集権限を復元できない。公開済みの記事自体は消去せず、従来の投稿者IDに紐付けて表示する。この制約を初回投稿・保存時と設定に短く案内する。端末間同期・アカウント連携・復旧手段は初回対象外。

### S6 Cloudflare配布とアップデート（提案）

- 本体はWorkers Static Assetsの静的配信を優先し、/api/*だけWorkerで処理する。Service Workerとバージョン情報も静的配信にし、更新確認のたびにD1を読む設計にしない。開発・プレビュー・本番のDBと秘密情報を分離する。
- 2026-10-18の公式資料で確認した無料枠: Workers 100,000リクエスト/日、CPU 10ms/呼出。D1は読取5,000,000行/日・書込100,000行/日、アカウント合計5GB、1DB最大500MB。静的アセット配信リクエストは無料・無制限。既存の同一アカウントの利用分も考慮する。枠内で収まるかは実際のクエリ計測で判断し、無料を永久保証しない。
- D1の行数はAPI回数と異なり、検索の走査行や索引更新も含まれる。カテゴリ/投稿者/講義/日時に索引、ページング、検索のデバウンスを設ける。閲覧記録は同日重複抑止用を短期間に限定し、累計は原子的に別保存する。期限切れセッションと古い重複判定記録を少量ずつ削除し、500MB上限への増加を抑える。
- Notion本文・画像はNotionから表示し、D1に複製しない。個人PDF・メモ画像・背景は端末内に置く。R2等の追加ストレージは初回不要。公開一覧のみ短期キャッシュ可、個人ブックマーク・セッションは共有キャッシュに入れない。
- 無料枠超過時はAPI/DBが失敗し得る。アプリ本体と個人データの操作を保ち、共有機能は一時利用不可と表示する。成功していない投稿/保存を成功表示せず、再試行ループを避ける。枠はUTC日次更新（日本時間09:00）。設定された無料プランのまま開始し、自動で有料へ切り替えない。
- 配布URLは固定し、原則同一オリジンのまま更新する。URL/ドメインを変えると端末内データ・匿名Cookieが別領域になるため、将来の移転は別途移行設計する。独自ドメインなしでも初回配布は可能。
- リリース手順: 検証→ビルドID・更新内容の生成→プレビュー用DBで確認→必要な互換DBマイグレーション→本番へアプリ/APIを配信→起動と投稿/保存をスモーク確認。Wranglerの手動配信を用意し、Git連携可能になれば指定した公開対象ブランチから検証成功時に配信する設定も用意する。実際のリポジトリ接続/本番公開はアカウントと公開先設定後。
- 起動時・オンライン復帰時・「その他→アプリの更新」の手動操作で更新確認し、フォアグラウンド中の確認間隔を制限する。アプリを閉じている端末へ即時更新を強制する保証はしない。OSのプッシュ通知は使わず、次回起動時等に検出する。
- 新版の必要アセットが取得できた時だけ「新しいバージョンがあります／保存して更新／あとで」を表示。IME変換・画像処理・PDF取込・未保存変更がある間は切替しない。保存完了と同一オリジンの全アプリタブの準備完了を確認し、新Service Workerを有効化→1回だけ再読み込み。応答しないタブがあれば、閉じるか保存する案内を出して待つ。
- 保存/ダウンロード失敗やオフラインでは旧版と入力を保ち再試行できる。起動HTML・Service Worker・更新情報は更新を検出できるキャッシュ方針、ハッシュ付きアセットは長期キャッシュ。APIとセッション応答をService Workerの汎用キャッシュへ入れない。
- IndexedDBの移行はトランザクションで失敗時に原本を保護する。DBとAPIは旧クライアントとの互換を維持し、破壊的変更は即時に行わない。古いタブの必要アセットも保持する。更新で匿名Cookie/ローカルデータを消さない。
- 運営向けに前バージョンのアプリ/APIへ戻す手順とDBバックアップ/復元手順を用意。コードのロールバックはDBの巻戻しを意味しない。問題版の修正は新しいビルドIDとして再配信し、インストール済みPWAでも次回確認から取得できるようにする。
