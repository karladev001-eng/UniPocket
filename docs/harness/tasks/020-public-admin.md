## 全体像と実装段階

一般利用者は共有URL→ログインなしでアプリを開く→端末の操作でホーム画面へ追加。管理者は別の管理用URL→Cloudflareで本人確認→運営画面へ進む。公開アプリと管理画面は別Worker/別originにし、共通D1の公開可能なレコードだけを公開APIが返す。公開URLはパスワードではなく、知った人が転送でき、第三者も到達可能になる。検索掲載を抑えるnoindexは付けるが、閲覧制限としては扱わない。

実装は以下の一式を順に進める提案で、部分実装が無条件に公開されない構成にする。

1. 保護された管理用Worker、管理APIの認証/権限、追記migrationと監査記録を作る。
2. 記事の非表示/再公開、下書き・公開前確認を持つお知らせ/アンケート、利用者の受信・回答、管理集計をローカル/保護previewで検証する。
3. 既存端末データを保持する更新と公開対象データを点検し、管理者以外が管理APIを操作できないことを確認する。
4. 具体的なURL・公開される共有データ・管理画面保護の結果を提示し、公開切替の最終確認を受けてから一般アプリのAccessだけを解除する。管理画面のAccessは維持する。

今回の成果物は仕様・モック。現時点でAccess解除、Cloudflare作成、D1 migration、実アンケート作成・告知・配信は行わない。

## 提案仕様と受入条件

### S1 URLから使えるアプリと、管理者だけの入口（AC1–3）

- **AC1 一般公開**: 既存アプリのoriginと現在のD1 database IDを継続使用し、端末のIndexedDB・匿名セッション・背景・予定・メモ、共有記事と投稿権限を維持する。管理画面保護と公開前チェック完了後、一般アプリに効く本人限定Accessだけを解除/公開例外化する。アカウント全体の保護や管理WorkerのAll trafficを解除しない。URLから開く、共有URLをコピー、iPhone/Android向けの追加手順を用意。iPhoneはOSの「ホーム画面に追加」が必要で、無操作のインストールを約束しない。URLを知る人以外も到達し得ることを公開確認に明記。一般APIに管理者権限を付けない。
- **AC2 管理者認証**: 新しい管理用Workerを別originで作り、既存所有者1名をCloudflare Accessで許可。一般利用者の匿名プロフィールとは完全に分ける。管理HTML・API・集計・CSVの全URLを保護する。バックエンドでもAccessの正当な署名・issuer/audience/有効期限と所有者の許可を検証し、メール名のHTTPヘッダーや画面のroleだけで認可しない。静的Assetsの内部routerでctx.accessが渡らない点を考慮し、JWT検証を使う案とする。管理画面にはSW/オフラインキャッシュを登録せずprivate/no-store。編集中にAPI認証が切れた場合はその場で入力を保持して再ログインを案内し、無条件reloadで捨てない。権限追加・複数管理者・パスワード新設は初版に含めない。
- **AC3 管理ホーム**: 「概要／記事／お知らせ／アンケート／集計」の5区画。PCはサイドナビ＋読みやすい一覧、スマホはコンパクトなメニューと1列の操作。概要は公開中記事・未確認の通報・公開中のお知らせ/アンケートを示し、そのまま該当一覧へ進める。日付基準は日本時間。初期表示を大きな説明・ボタンで占有しない。

### S2 登録後すぐ公開し、運営で整える（AC4–5）

- **AC4 記事の管理**: 記事は従来どおり即時公開。管理者は題名・投稿者表示名・カテゴリ・公開/非表示状態で検索し、閲覧/ブックマーク数、元Notionリンクを確認できる。非表示は理由を入力→対象を確認→実行し、再公開が可能。記事本文はNotionの管理領域で、アプリ側非表示がNotion元ページ自体を削除/非公開にするとは扱わない。元の記事・著者・件数を保持する。作者は非表示状態を変更して再公開できない。管理者が本人になりすます、著者の記事内容を書き換える、取り消せない一括削除は初版に含めない。
- **AC5 通報と非表示の反映**: 記事詳細の補助メニューから理由（不適切・誤情報・リンク不備・その他、補足最大500文字）を送信。匿名セッションごと同一記事の未処理通報を重複作成しない。管理者は通報を未確認/確認済みにし、必要なら記事非表示へ進める。非表示記事は人気/新着/検索/投稿者/ブックマーク一覧と公開詳細APIから除外し、直リンクも非公開として扱う。非表示記事へのview/bookmark送信と、非表示変更に競合した更新もサーバー側で拒否する。作者専用の自分の投稿一覧では状態と作者向けの理由を確認でき、作者本人の編集/削除権限を保つが、管理非表示状態は解除できない。作者削除はdeletedとして管理の再公開対象からも外し、識別・監査に必要な最小の記録を残す。古い取得済みカードは次回取得/前面復帰で除去し、すでに画面へ表示した内容や元Notionページを遠隔で消せるとは約束しない。記事表示時は公開状態を再確認し、通信不能時はキャッシュしたNotion埋め込みを新たに開かない。

### S3 小さく届くお知らせと任意のアンケート（AC6–8）

- **AC6 お知らせ配信**: 管理者は題名80文字・本文2000文字・任意のリンク1件（httpsのみ）・表示開始/終了日時を編集し、下書き→利用者表示プレビュー→公開確認→公開と進める。開始日時が未来なら予約扱い、期限到達/手動終了で一覧から外れる。公開条件はサーバーの日時で判定し、ジョブ遅延に依存しない。公開済み本文の編集は改訂版として確認し、既読状態はその版ごとに扱う。二重送信/失敗再試行で重複作成しない。未保存の入力は離脱確認/保存失敗時保持。公開終了は取り消せる操作として確認する。
- **AC7 利用者の受信**: ホーム上端に小さなベル＋未読数と、今日/次の予定の下に最新お知らせ・回答募集中アンケートを合わせて最大1行の案内にまとめる。大きなバナーで予定を押し下げない。「すべて」からお知らせ一覧へ。既存下部5タブは増やさず、その他にもお知らせ入口を置く。開いたお知らせの版だけその端末内で既読にし、既読情報はサーバーへ送信しない。初回は全員向け・アプリ内のみ、アプリを開かない端末へOS通知やメールは送らない。期限切れ/取得失敗/0件/オフラインは区別し、本文の取得に失敗しても予定・メモを使える。
- **AC8 アンケート**: 管理者は題名・紹介・表示開始/締切、最大10問（単一選択/複数選択/自由記述、選択肢最大10、自由記述1000文字、必須/任意）を下書きで作成。プレビューと公開確認後に回答可能。同じ匿名ユーザーIDは1アンケート1回答で、再送は同じ結果を返し二重計上しない。「1人1回」や別ブラウザとの同一人物判定は保証しない。回答は任意で、回答しなくてもアプリを使える。入力/送信中/成功/締切到達/重複/通信失敗を用意し、失敗時は入力保持。公開後の設問・選択肢は変更不可（複製して新規版を公開）。題名・紹介・締切は確認して変更可。選択集計・回答数・匿名の自由記述を管理者だけが確認しCSV出力できる。自由記述入力に短く個人情報を避ける案内を置く。公開された一般APIから全回答や他人の回答を取得できない。

### S4 記事と回答の結果を確認する（AC9–10）

- **AC9 集計**: 管理画面「集計」は7日/30日/任意期間（最大90日）、日本時間で記事の日別閲覧数・期間内閲覧数、現在のブックマーク数、アンケート回答数・選択結果を表示。自由記述はアンケートの結果画面から別操作で確認/CSV出力。現在のブックマークは集計時点の値で期間選択では変わらない。記事閲覧/回答の日次集計を追加し、既存view_eventsの短期保持だけへ依存しない。日次データは日付・記事/アンケートID・件数と確定時刻だけを持ち、利用者IDや行動履歴を持たない。回答数は受付日時で日別に計上。閲覧の定義・重複除去と人気記事の直近7日スコアは019を継承し、累計閲覧とは分ける。過去へ復元できない値は「集計開始日以降」/未収集とし0埋めしない。0・未収集・取得失敗、集計時刻と定義を区別。集計CSVは日付・対象コンテンツID/題名・件数・集計時刻のみで利用者識別子を含めない。PWAのダウンロード/インストール推移は初版の対象外とし、カード・グラフ・推定値を出さない。
- **AC10 データの範囲**: 利用状況の追加送信を設けない。起動・画面種類/遷移・インストール/standaloneイベント・訪問者/ブラウザ数は収集せず、協力設定/同意UI、usage送信API/テーブルも作らない。お知らせの既読は版ごとに端末内だけで保持し、開封送信・サーバー既読・開封数/率の集計をしない。記事の取得/閲覧・ブックマーク・投稿・通報、匿名セッション、任意のアンケート回答など機能に必要なリクエストは残るため、「通信を一切しない」とは案内しない。予定/PDF/メモ/背景/検索文/URLクエリ/精密な位置情報を収集しない。IP・端末指紋を集計へ保存しない（不正対策の既存rate limitは別用途）。保持上限は記事閲覧の明細30日、終了アンケートの個別回答は終了後90日、コンテンツ日次集計と管理監査365日を提案。集計は期限前に確定し、削除失敗は監視して再実行。一般APIに利用者別の行動履歴を返さない。

PWAのインストール検知は環境によって利用可否が異なり、Chromiumの`appinstalled`やAndroidの追加承諾でも全環境の完了数を保証できない。このため正確なダウンロード推移の代わりにアクセス数やasset取得を代用しない。将来、定義と対応環境を改めて検討できる構成に留める。[web.dev: PWA detection](https://web.dev/learn/pwa/detection)、[MDN: appinstalled event](https://developer.mozilla.org/en-US/docs/Web/API/Window/appinstalled_event)（2026-10-20確認）。

### S5 公開前に守る境界と移行（AC11–12）

- **AC11 整合性・公開運用**: 管理更新の競合はrevisionで検出し409として入力保持。公開/非表示/再公開/終了/CSV出力は管理者・対象・日時・操作結果の監査ログへ記録し、本文や認証tokenをログへ出さない。監査記録が必要な更新はD1の同じtransaction/batchで成立させ、途中失敗で片方だけ更新しない。入力上限・HTTPSリンク検証・XSS防止・CSRF/Origin検証、匿名IDとIPのrate limitを維持/拡張。現行のセッション作成10回/時/IPは共有Wi-Fiを想定して再設計し、同一IPの100利用環境が連続初回起動できる負荷ケースと不正連投の抑止を検証する。IPだけを同一人物判定に使わない。公衆向けの投稿/通報/回答の連投を制限し、機密値をCSVへ混ぜず表計算式として実行されるセルを無害化。無料枠から始め、有料プランへ自動変更しない。上限/障害時は共有機能だけに再試行を提示し、端末内の予定・メモと安全な更新は保つ。
- **AC12 受入・公開切替**: 320×640/390×700/PCで主要画面と主要状態、44px操作域、入力16px、キーボード/フォーカス/単一閉じる操作を確認。実D1で非表示の全経路、二重回答/締切/競合/集計/保持期限、偽造管理者・期限切れ/別audienceの認証拒否、CSVと監査を検証。一般URLの未認証利用と管理URLの未認証拒否を別々に確認し、管理WorkerのAccessとサーバー認可を確認してから公開切替する。実装時のlocal/保護previewと、一般公開の最終操作を分ける。公開時は共有DBの既存検証記事を点検して対象を確定し、予定/メモや記事投稿者の権利を自動リセットしない。016の旧iPhone復旧未完了を引き継ぎ、公開切替だけでその端末が直ったとは報告しない。

## 構成とデータ案

- 既存の公開用Worker/ASSETS/D1を拡張。既存originを維持し、一般ユーザーは匿名セッションで記事・回答等を行う。共有URL/インストール案内は既存その他内の追加手順を再利用する。
- 管理用Worker（提案名uni-pocket-admin）を別構成で作り、ASSETSも含む全体をAccessで保護。管理APIは同originで検証し、D1だけを共有。公開アプリ側に管理APIへの迂回経路を作らない。
- 追記migration案: articlesの可視性/revision/非表示理由、article_reports、announcements/revisions、surveys/questions/options/responses/answers、daily_content_metrics（日付・コンテンツID・件数・確定時刻）、admin_audit。既存profiles/sessions/bookmarks/view_eventsを再利用し、通常メモ/予定DBをサーバーへ移さない。
- 公開API案: 公開中のannouncements/surveysの取得、通報/回答の検証付き送信。お知らせの既読は端末内だけで、既読送信を設けない。管理API案: 状態絞込一覧、revision付き編集/公開/非表示/終了、集計とCSV。API/テーブルの細分は実装契約で確定し、仕様上の権限境界を変えない。
- 管理者以外の匿名投稿は引き続き即時公開。管理者は本人確認済みの所有者のみ。一般ユーザー名を管理者判定に使わない。
